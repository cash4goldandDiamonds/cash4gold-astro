# Launch monitoring and indexing

**NOT TESTED — future phase.** No release, indexing submission, recurring alert or phone delivery test was performed by this checklist.

## Before cutover

Establish the owner's actual alert destination and a monitored operator, then test notification delivery. Record expected hours of coverage and escalation. Verify an uptime check and a safe genuine inquiry-delivery test, privacy-safe analytics debug events, correct Search Console ownership, sitemap and rollback identity. Do not assume minimizing the app creates a phone notification or that this computer stays awake.

## Launch day and first 24 hours

- Check HTTPS/canonical host, real GET/HEAD and 404, important old URLs and approved 301s, robots/noindex absence on intended production pages, sitemap canonical entries, phone/navigation and actual form delivery.
- Verify no draft/preview/internal audit file, secret or private content is public. Confirm mail DNS and unrelated services remain intact.
- Submit the sitemap in the correct Google Search Console property; record actual submission time/status. Use supported URL Inspection requests for important eligible URLs within current quotas and inspect a representative sample. Sitemap submission and requested indexing are not proof of indexing. Do not use the Google Indexing API for ordinary jewelry articles.
- Check analytics consent and privacy-safe conversion events without real customer PII. Compare against the recorded baseline, with the date range/collection changes clearly stated.
- Inspect Cloudflare errors, missing media, redirects, logs, inquiry failure/delivery, CMS build failures and social failed/uncertain jobs. Alert the owner only through the tested channel.

## Days 1–7, 14 and 30

Review crawl/indexing and Google-selected canonicals, soft 404s, coverage changes, top landing-page/query traffic, inquiry delivery/conversions and lost source URLs. Compare local ranking tracker results for the same keywords, geography, device and date cadence; don't claim attribution from raw position changes. Audit broken links/new media and CMS publishing workflows after real editor use. Resolve incorrect content through approved changes with retained history.

Review field Core Web Vitals when sufficient real data exists; lack of field data is not a pass. Targets at the 75th percentile: LCP <=2.5 s, INP <=200 ms, CLS <=0.1. Lab targets: mobile performance >=90, desktop >=95 and other relevant Lighthouse categories >=95. Run three tests for each representative route/device; retain median, worst, raw report, timestamp and release identity.

Review social token expiry/renewal, exact account ownership, publishing receipts, missed slots, held drafts, UTM traffic and queue integrity. Three weekly posts is a cadence, not a traffic/ranking guarantee. Retain backup/artifact history until the owner accepts stable operation; never delete rollback resources merely because a fixed number of days elapsed.
